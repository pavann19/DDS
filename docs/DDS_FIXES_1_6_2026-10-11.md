# DDS fixes 1–6 — local implementation and validation

Target confirmed by the user: a real-road simulator with explicitly simulated
vehicle and sensors. Real coordinates do not imply verified road rules. ML
remains vehicle-reading analytics; driving controls remain in the deterministic
driver/planner and independent safety systems.

Cruise preference now supports 30, 50, 60, 80, 100 and 120 km/h; traffic, grip,
curvature and destination approach still constrain actual motion. This setting
is not a posted legal speed limit. Default remains 50 km/h; the live validation
trip used 80 km/h.

## Additional defects found during implementation

- Tracker lag/coasting could create phantom emergency braking on the curved
  road. Immediate geometry now uses a source-free post-noise measurement feed,
  separate from display tracking. The curve regression passes after removing
  coasted estimates from that immediate feed.
- Detected vehicle headings had defaulted to zero, leaving occupancy rectangles
  incorrectly aligned. Heading now follows the measured velocity direction.
- The comfort-jerk test contained unseeded random collision traffic. It now
  isolates deterministic unobstructed comfort motion; the separate emergency
  test still requires braking to bypass the comfort jerk bound.
- Lead-distance UI used the nearest surrounding actor and implied a clear road
  when none was detected. It now reports the forward sensed lead gap or
  `Not detected`.
- Set speed displayed the momentary braking target (zero at arrival) instead
  of the configured cruise preference. It now retains the configured value;
  the browser confirmed Set speed 80 with actual speed 0 at arrival.
- A source encoding error introduced during editing caused a Next compilation
  failure. It was corrected and the frontend rebuilt.
- Final browser validation caught `NaN` in the speed animation. A browser RAF
  timestamp was observed preceding `performance.now()` by about 26 ms; the
  tween allowed negative interpolation progress. Progress is now clamped at
  both ends and non-finite animation state recovers to a finite target. An
  injected early-timestamp browser check displayed the offline dash before
  connection and finite zero-speed readings afterward, without NaN. The
  destination-reached browser check also showed zero after this change.
- Existing Frenet documentation calls positive lateral displacement right,
  although the coordinate implementation is left-positive. The new sweep check
  follows the implementation. A global convention migration remains separate.

## Executed validation

Actual browser observations included blocked OSM tile requests, Retry recovery,
both endpoint labels in route overview, backend disconnection/reconnection,
80 km/h set speed, actual cruising at 80 km/h, road continuation, and the
destination-reached display. Screenshots were visually inspected, including
`output/playwright/cockpit-redesign/fixes-map-overview-final.png` and
`fixes-arrived-map.png`. Nine browser network errors were expected from deliberate
tile blocking; they are not a clean-console claim.

Live WebSocket evidence is in `output/fixes-live-scenarios.json`: all eight
scenario commands applied; a malformed friction command was rejected with
unchanged physical state and epoch. `output/fixes-80kmh-trip-live.json` records
the trip; arrival means below 1 km/h at the capture stop condition, not proof of
parking. These are sampled observations, not a success-rate estimate.

and 453 passed / 3 failed / 3 skipped. Follow-up checks resolved the functional
failures (interface contract and phantom braking); timing remained unresolved.

The final full suite (`output/fixes-final-suite.txt`) completed with **456 passed,

An additional moving-drive browser sample after reset is recorded in

Backend and frontend were left running on ports 8000 and 3000. The drive was
reset after the arrival capture and retained the 80 km/h preference for manual
inspection. This does not resolve the parking/semantics/runtime items above.

The final-code live trip captured 1,444 frames, reached 80 km/h, and reported
ARRIVED at simulation time 185.4 s with 0.973 km/h and 1.93 m remaining. The
browser subsequently showed 0 km/h, Destination reached, and Stopped · parking
location unverified. At capture, stage deadline-miss counts included perception
2 and control/safety/physics 7; maximum scheduling lateness was 214.73 ms. A
real-time factor of 1.0 did not eliminate those misses.

## Parking and road-rule boundary

Public Overpass requests for nearby parking returned HTTP 406, 500 and 504
across attempted endpoints. No parking dataset was installed from those
requests. A lot's presence alone would not prove a reachable parking bay or
permitted maneuver. The remaining work needs a provenance-preserving road and
parking dataset, semantic validation, a route into accessible parking geometry,
a bounded low-speed parking planner, and browser/live maneuver validation.
No fabricated bay or inferred shoulder was marked as real mapped data.
